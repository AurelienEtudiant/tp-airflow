Cahier des charges — Projet C : NewsRadar

Version : 3.0 (avril 2026) Pitch : pitch.md · Règles communes : Documentation commune.html

1. Contexte

Vous êtes Data Engineer dans NewsRadar Intelligence, une startup française spécialisée dans la veille média automatisée pour grands comptes (banques, assurances, industriels). NewsRadar agrège quotidiennement des milliers d'articles de presse depuis des centaines de sources hétérogènes, les enrichit via du NLP (classification thématique, analyse de sentiment, extraction d'entités), et les expose via un moteur de recherche full-text à ses clients abonnés.

Chiffres (fictifs) :

  • 8 000 articles traités par jour
  • 450 sources actives (presse en ligne, blogs, communiqués de presse, APIs)
  • 75 clients abonnés
  • SLA : un article publié doit être indexé en < 30 min

Le besoin

L'infrastructure actuelle est un script Python monolithique (~3000 lignes) écrit en 2023 par un ancien stagiaire. Il scrape, classifie et stocke dans une vieille version d'Elasticsearch. Problèmes :

  • 🔴 Script instable, plante 2-3 fois par semaine
  • 🔴 Aucun monitoring : on découvre les pannes via les clients
  • 🔴 Le modèle ML est appelé article par article → ingestion 5x plus lente que nécessaire
  • 🔴 Pas de déduplication → certains articles sont indexés 3 fois
  • 🔴 Elasticsearch 7.x en fin de support, licence restrictive

Votre mission

Reconstruire la plateforme :

  1. Airflow comme orchestrateur (visibilité, retries, alerting natif)
  2. Custom Hooks par type de source (RSS, API, scraping HTML)
  3. Service ML dédié (FastAPI + HuggingFace) appelé en batch
  4. Déduplication par hash URL + titre
  5. OpenSearch comme moteur de recherche (fork open-source d'Elasticsearch)
  6. Tests pour rendre le tout maintenable

L'objectif pédagogique principal est de combiner Airflow avec des services externes via HTTP : c'est le pattern le plus courant en production data quand on doit interagir avec du ML, des APIs internes, ou des moteurs de recherche.

2. Objectifs pédagogiques

  • 🟢 Orchestrer un pipeline multi-sources hétérogènes avec Airflow 3.1.8
  • 🟢 Utiliser Dynamic Task Mapping (.expand()) pour traiter N sources en parallèle
  • 🟢 Implémenter plusieurs Custom Hooks (RSS, API, scraping)
  • 🟢 Concevoir et déployer un service ML externe (FastAPI + HuggingFace Transformers)
  • 🟢 Appeler ce service depuis Airflow en batch (pas article par article)
  • 🟢 Dédupliquer des données avec hash + contraintes UNIQUE
  • 🟢 Indexer et rechercher dans OpenSearch 3.6
  • 🟢 Visualiser les résultats dans OpenSearch Dashboards
  • 🟢 Superviser le pipeline avec Prometheus + Grafana (bonus)

3.2 Flux d'enrichissement ML

sequenceDiagram
    participant A as Airflow task
    participant P as PostgreSQL
    participant N as nlp-service
    participant H as HuggingFace models
    participant O as OpenSearch

    A->>P: SELECT articles WHERE enriched = false LIMIT 50
    P-->>A: batch 50 articles
    A->>N: POST /enrich {batch: [50 articles]}
    N->>H: classify_batch(texts)
    H-->>N: topics
    N->>H: sentiment_batch(texts)
    H-->>N: sentiments
    N-->>A: 50 enrichissements
    A->>P: UPDATE enriched=true + INSERT fact_enrichment
    A->>O: bulk index 50 documents
    O-->>A: ack

3.3 Pourquoi cette architecture

  • Service ML séparé : si on charge HuggingFace dans les workers Airflow, chaque worker = ~2 Go de RAM consommés en permanence. Avec un service dédié, le modèle est chargé une seule fois et les workers font des appels HTTP légers.
  • Batch d'enrichissement : appeler le NLP service article par article = 8 000 requêtes HTTP/jour. Avec des batches de 50, c'est 160 requêtes/jour. 50x moins de overhead réseau.
  • OpenSearch plutôt qu'Elasticsearch : licence Apache 2.0 (vs SSPL pour ES 8+), 100% compatible API ES 7.x, fork actif et bien maintenu.
  • PostgreSQL + OpenSearch en parallèle : PostgreSQL stocke les metadata (qui assure la déduplication par contrainte UNIQUE), OpenSearch stocke le document complet pour la recherche full-text. C'est le pattern dual-store classique.
  • Dynamic Task Mapping : permet de traiter N sources en parallèle sans hardcoder les noms. Nouvelle source = nouvelle ligne en base, pas de modification de DAG.

4.2 OpenSearch — configuration critique

OpenSearch est exigeant en mémoire. Pour tourner sur une machine en formation :

  opensearch:
    image: opensearchproject/opensearch:3.6.0
    ports:

      - "9200:9200"
      - "9600:9600"
    environment:

      - cluster.name=newsradar-cluster
      - node.name=opensearch-node1
      - discovery.type=single-node
      - bootstrap.memory_lock=true
      - "OPENSEARCH_JAVA_OPTS=-Xms512m -Xmx1g"
      - "DISABLE_SECURITY_PLUGIN=true"        # FORMATION UNIQUEMENT
      - "DISABLE_INSTALL_DEMO_CONFIG=true"
    ulimits:
      memlock:
        soft: -1
        hard: -1
      nofile:
        soft: 65536
        hard: 65536
    volumes:

      - os-data:/usr/share/opensearch/data
    networks:

      - airflow-net

  opensearch-dashboards:
    image: opensearchproject/opensearch-dashboards:3.6.0
    ports:

      - "5601:5601"
    environment:

      - 'OPENSEARCH_HOSTS=["http://opensearch:9200"]'
      - "DISABLE_SECURITY_DASHBOARDS_PLUGIN=true"
    depends_on:

      - opensearch
    networks:

      - airflow-net

🔴 DISABLE_SECURITY_PLUGIN=true est exclusivement réservé à la formation. En production, c'est une faille de sécurité critique. Documentez ce choix dans le README.

🟠 Sur Linux, OpenSearch peut refuser de démarrer avec Max virtual memory areas vm.max_map_count [65530] is too low. Solution : sudo sysctl -w vm.max_map_count=262144 (à rendre permanent dans /etc/sysctl.conf).

4.3 Service NLP — configuration

  nlp-service:
    build:
      context: ./nlp-service
      dockerfile: Dockerfile
    ports:

      - "8000:8000"
    environment:

      - MODEL_SENTIMENT=distilbert-base-uncased-finetuned-sst-2-english
      - MODEL_CLASSIFY=facebook/bart-large-mnli
      - HF_HOME=/root/.cache/huggingface
    volumes:

      - hf-cache:/root/.cache/huggingface     # CRITIQUE : cache des modeles
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 5
    networks:

      - airflow-net

volumes:
  hf-cache:

🟠 Le volume hf-cache est CRITIQUE. Sans lui, HuggingFace re-télécharge les modèles à chaque docker compose up (~2 Go, 3-5 minutes). Avec le volume, le 2ème démarrage prend < 30 secondes.

9.4 Dynamic Task Mapping — pattern

Le DAG d'ingestion doit utiliser .expand() pour traiter les sources en parallèle :

# Pseudo-code - a vous d'implementer
@dag(...)
def newsradar_ingest_daily():
    @task()
    def get_active_sources() -> list[dict]:
        # SELECT depuis dim_source WHERE type='rss' AND is_active=true
        return [...]

    @task()
    def fetch_source(source: dict) -> str:
        # Utilise le bon Hook selon source['type']
        # Upload raw dans MinIO
        # Retourne le chemin S3 (PAS le contenu)
        return f"raw/rss/dt=.../{source['source_id']}.json"

    @task()
    def consolidate(s3_paths: list[str]) -> int:
        # Lit tous les fichiers MinIO
        # INSERT ... ON CONFLICT (url_hash) DO NOTHING
        return inserted_count

    sources = get_active_sources()
    paths = fetch_source.expand(source=sources)
    consolidate(paths)

🟠 Important : fetch_source ne doit JAMAIS retourner les articles eux-mêmes (sinon XCom volumineux). Retournez le chemin S3 et lisez depuis S3 dans la task suivante.

11. Découpage du projet

11.1 — Ingestion + enrichissement ML

L'objectif de la 1ere partie est d'avoir un pipeline d'ingestion fonctionnel avec déduplication et enrichissement ML par batch. À la fin de la journée, vous devez avoir ≥ 100 articles dans fact_article avec enriched = true, et le nlp-service qui répond sur /health.

Étapes recommandées dans l'ordre :

  1. Démarrer le stack sans OpenSearch dans un premier temps (docker compose up -d minus opensearch). Le téléchargement des modèles HuggingFace prend 2-3 min au premier lancement — c'est le bon moment pour explorer le code des fixtures.
  2. Concevoir le schéma PostgreSQL : dim_source, fact_article, fact_enrichment. Écrivez le SQL avec les contraintes UNIQUE sur url_hash et title_hash.
  3. Implémenter 2 Custom Hooks : commencez par le plus simple (RSS avec feedparser), puis ajoutez le News API. Le HTML scraping est plus chronophage.
  4. Tester chaque Hook isolément dans un script Python avant de l'intégrer dans un DAG. Vérifiez que tous retournent le format commun (url, title, body, published_at, source_id).
  5. Écrire le DAG d'ingestion avec Dynamic Task Mapping. Pattern : get_sources → fetch.expand(source=...) → consolidate. Attention : fetch doit retourner un chemin S3, pas les articles.
  6. Implémenter la déduplication : INSERT ... ON CONFLICT (url_hash) DO NOTHING. Vérifier qu'aucun doublon n'est créé en relançant 2 fois le DAG.
  7. Écrire le nlp-service FastAPI avec les 2 endpoints minimum (/classify, /sentiment). Tester avec curl que les modèles répondent.
  8. Écrire le DAG d'enrichissement : SELECT articles WHERE enriched=false LIMIT 50, POST en batch au nlp-service, UPDATE enriched=true. Par batch de 50, pas article par article.

🟢 Objectifs : : ≥ 100 articles ingérés, dédupés et enrichis. Premier commit Git poussé.

🟠 Conseil : démarrer OpenSearch consomme de la RAM. Tant que vous ne touchez pas à OpenSearch (J2), gardez-le arrêté avec docker compose stop opensearch opensearch-dashboards pour libérer ~1 Go.

🟡 En cas de retard : sacrifiez le 3ème Hook (HTML scraping) et restez sur RSS + API. Vous perdrez des points sur les bonus mais vous garderez un MVP cohérent.

11.2 — OpenSearch + dashboards + finition

La deuxième partie est dédiée à l'indexation des articles enrichis dans OpenSearch et à l'exposition des résultats via OpenSearch Dashboards. L'objectif est qu'un analyste puisse rechercher dans les articles via une interface web.

Étapes recommandées dans l'ordre :

  1. Démarrer OpenSearch : docker compose up -d opensearch opensearch-dashboards. Vérifier avec curl http://localhost:9200/_cluster/health que le cluster est green ou yellow (yellow est OK en single-node).
  2. Créer le mapping de l'index articles via un script d'init ou un appel PUT /articles en Dev Tools. Ne laissez pas OpenSearch deviner les types — c'est plus propre de définir le mapping.
  3. Écrire le DAG d'indexation OpenSearch : SELECT articles enrichis non-indexés → bulk index via opensearch-py. Le bulk index est 5-10x plus rapide que des requêtes index individuelles.
  4. Tester la recherche via Dev Tools : GET /articles/_search?q=tech doit retourner des résultats pertinents.
  5. Créer 1 dashboard OpenSearch Dashboards (bonus Should) avec au moins 3 visualisations.
  6. Bonus si avance : choisir une option Could (observabilité OU NER + Search API). Voir §13.
  7. Écrire les tests pytest (au moins 3) : import sans erreur, structure du DAG d'ingestion, déduplication idempotente.
  8. Finaliser le README avec le schéma Mermaid de l'architecture et les choix techniques justifiés.

🟢 Objectifs : : ≥ 100 documents dans OpenSearch, recherche fonctionnelle, dashboard OpenSearch Dashboards, tests qui passent.

🟠 Conseil : si vous voulez tenter l'observabilité (Option A), commencez avant le dashboard OpenSearch Dashboards. C'est plus chronophage qu'on ne le pense.

Piège Symptôme Solution

Piège Symptôme Solution
🔴 Re-téléchargement à chaque up Démarrage lent (2-3 min) Volume hf-cache sur /root/.cache/huggingface

Piège Symptôme Solution
🔴 Pas de retry Un 503 → DAG crash retries=3, retry_delay=timedelta(seconds=30)
🔴 Timeout trop court Tasks fail en charge timeout=60 sur les appels nlp-service
🔴 Appels 1 par 1 Ingestion 50x trop lente Batch de 20-50 minimum
🟡 Wrong host "Connection refused" http://nlp-service:8000 (pas localhost)

15.5 PostgreSQL — déduplication

Piège Symptôme Solution
🔴 Pas d'index sur url_hash Déduplication très lente CREATE INDEX idx_url_hash ON fact_article(url_hash);
🔴 ON CONFLICT non utilisé Erreurs duplicate key INSERT ... ON CONFLICT (url_hash) DO NOTHING
🟡 Hash non normalisé Doublons malgré le hash sha256(url.strip().lower()) — toujours normaliser

17. FAQ

Q : Les modèles HuggingFace sont énormes, on peut utiliser autre chose ? R : Oui — utilisez distilbert-base-uncased-finetuned-sst-2-english (260 Mo) + un classifier maison basé sur TF-IDF + scikit-learn. Documentez le choix dans le README.

Q : OpenSearch ne démarre pas sur Linux. R : sudo sysctl -w vm.max_map_count=262144. Pour rendre permanent : ajouter dans /etc/sysctl.conf.

Q : On peut utiliser Elasticsearch 8.x à la place d'OpenSearch ? R : L'API est compatible mais la licence ES 8+ est restrictive (SSPL). Restez sur OpenSearch.

Q : Le nlp-service est lent (10s par article). R : Vous appelez probablement le service article par article. Batchez les requêtes (50 textes en 1 POST). Utilisez la méthode pipeline(...) de transformers qui supporte les batches nativement.

Q : On a choisi l'option NER + Search API, on peut aussi faire l'observabilité ? R : Non, choisissez une seule option Could. Les deux en 14h c'est irréaliste.

Q : Comment on teste les Hooks sans Airflow ? R : Créez un script Python qui instancie le Hook directement (from plugins.hooks.rss_hook import RSSHook; hook = RSSHook(); hook.fetch_feed("fixtures/rss/lemonde.xml")). C'est plus rapide pour itérer.

Q : Le DISABLE_SECURITY_PLUGIN=true est vraiment nécessaire ? R : Oui en formation. En prod jamais — vous configureriez les utilisateurs, les rôles, les certificats TLS, etc. C'est ~1 jour de travail à part entière.

🟢 Objectif final : 100+ articles ingérés → dédupés → enrichis ML → indexés → cherchables. Propre, testé, démontrable en live.
